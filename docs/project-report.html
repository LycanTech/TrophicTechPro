Overview

Executive Summary

Mission Control is a full-stack internal dashboard purpose-built for Trophic Tech's engineering teams to manage real-time deployment activity across all active client engagements. It provides animated metrics, a searchable command palette, filterable deployment pipelines, and project tracking — all behind JWT-authenticated sessions with role-based access.

The platform is deployed on Azure Kubernetes Service via a six-stage GitHub Actions CI/CD pipeline featuring security scanning, automated testing, Docker image publishing to Azure Container Registry, Helm-based canary + full rollouts, and a manual approval gate guarding every production promotion. The entire cloud infrastructure is defined in Terraform across six reusable modules.

6 CI/CD pipeline stages Security → Test → Build → Staging → Approval → Production
6 Terraform modules Networking, AKS, ACR, Database, Key Vault, Monitoring
6 Client projects tracked Capital One, Nordstrom, Microsoft, Nike, Salesforce, Wells Fargo

Architecture

System Architecture

The entire stack lives in Azure East US 2. A single AKS cluster hosts three namespaces: staging, production, and monitoring. All inbound HTTP traffic routes through a shared nginx-ingress controller backed by an Azure Standard Load Balancer. PostgreSQL is accessed via private VNet injection — no public endpoint is ever exposed.

Continuous Integration & Delivery

CI/CD Pipeline

The pipeline is defined in .github/workflows/main.yml and follows a two-branch promotion model. Pushing to dev runs Jobs 1–4 and deploys to the staging namespace for continuous validation. Merging a PR to main triggers the full six-stage pipeline through to production. 

dev / feature/*  ──►  push to dev  ──►  Jobs 1–4  (CI + Staging deploy)
                                               │
                                       PR merge to main
                                               │
                                               ▼
                            main push  ──►  Jobs 1–6  (CI + Approval Gate + Production)
🔍

Job 1 — Security & Lint

ESLint SARIF output uploaded to the GitHub Security tab. Trivy filesystem scan for secrets and CVEs. Both checks are non-blocking — findings are surfaced without halting the pipeline.

Trivy fs ESLint SARIF GitHub Security tab Non-blocking
🧪

Job 2 — Unit & Integration Tests

Jest test suite runs against a real Postgres 16 service container (not mocked). Coverage report is uploaded to Codecov. Failures here block the build — the pipeline does not proceed without green tests.

Jest Postgres 16 service Codecov 60% coverage threshold Blocking
🐳

Job 3 — Build & Push to ACR

Three-stage Dockerfile built with BuildKit layer caching (deps → builder → runner). Image is tagged with the commit SHA and also tagged latest on main. Trivy image scan + SBOM generated and uploaded as SARIF. Authentication uses OIDC — no credential blobs stored as GitHub secrets.

BuildKit Multi-stage Dockerfile Trivy image scan SBOM OIDC
🟡

Job 4 — Deploy → Staging

nginx-ingress is installed (or upgraded) idempotently with externalTrafficPolicy=Local. Key Vault secrets are pulled and materialised as a Kubernetes Secret. A Kubernetes batch/v1 Job runs prisma migrate deploy && node prisma/seed.mjs — migrations are applied and demo data seeded on first run. Helm deploys atomically with a 10-minute timeout. Smoke test runs kubectl exec into the pod and checks /api/health returns "status":"ok" — bypassing LoadBalancer, ingress, and DNS entirely.

nginx-ingress (externalTrafficPolicy=Local) Key Vault CSI Prisma migrate seed.mjs Helm --atomic kubectl exec smoke test
🔐

Job 5 — Manual Approval Gate

Pipeline pauses at the production-approval GitHub Environment. A required reviewer must approve before any production traffic is touched. This is a hard gate — no bypass, no timeout auto-approve.

GitHub Environment Review Required reviewer Manual
🟢

Job 6 — Deploy → Production

Checks that the PostgreSQL Flexible Server is in Ready state — auto-starts if Stopped (common after Azure auto-pause on the staging-tier DB). nginx-ingress installed with same settings. Migrations + seed run. Canary deployment at 20% traffic (1 replica, 30 s soak) precedes the full rollout to 3 replicas. Canary is then cleaned up. Health check runs kubectl exec into the production pod — same in-cluster approach as the staging smoke test. Slack notification sent on success or failure.

PostgreSQL readiness check Canary 20% · 30 s soak 3 replicas full rollout kubectl exec health check Slack notify

Engineering Decisions

Key Decisions & Post-Mortems

Several non-obvious problems were diagnosed and solved during the build and deployment of this platform. Each decision below reflects a real production incident, its root cause, and the fix applied.

Incident 1 — ERR_CONNECTION_TIMED_OUT on every browser request Resolved

Symptom: Chrome showed ERR_CONNECTION_TIMED_OUT. The app was reachable from inside the AKS cluster (HTTP 200 from kubectl exec) but not from the public internet.

Root cause: Azure Standard Load Balancer distributes inbound traffic across ALL nodepools in the backend pool — both the system pool and the app pool. The AKS health probe checks the NodePort (31151) on both nodes and passes (kube-proxy forwards via iptables on all nodes). The LB therefore considers both nodes healthy and round-robins ~50% of traffic to each. The system nodepool subnet NSG (trophic-staging-nsg-aks-system) had only a DenyInternetInbound rule and no allow rule for HTTP traffic. Azure Standard LB evaluates NSG rules after DNAT — the destination IP at NSG evaluation time is the node's private IP, so the LB's own public IP (68.220.239.81) in the existing NSG allow rule never matched. Half of all requests were silently dropped.
Problem identified: Internal curl works, external browser times out → NSG issue, not application.
First check: Single NSG on app nodepool had correct allow rule (port 80/443, Internet → *). System nodepool NSG not examined.
Fix 1 (immediate): Added AllowHTTPFromInternet (port 80/443, priority 200) and AllowNodePortsFromInternet (30000–32767, priority 150) to trophic-staging-nsg-aks-system.
Fix 2 (permanent): Patched the live ingress-nginx service with externalTrafficPolicy=Local. This signals to the Azure Cloud Controller that only nodes running the ingress-nginx pod should be included in the LB backend — app nodepool only. The system nodepool is excluded, making its NSG irrelevant to the traffic path.
Fix 3 (CI-persistent): Added --set controller.service.externalTrafficPolicy=Local to both nginx-ingress Helm install steps in the workflow, so the setting survives every future deploy.
Verified: HTTP 200 from local machine: {"status":"ok","db":"connected"}
Incident 2 — Smoke test failing with HTTP 000 / exit code 28 Resolved

Symptom: Staging smoke test and production health check both failed with HTTP 000 (curl: TCP connection never established) or exit code 28 (curl timeout) when hitting the nip.io hostname.

Root cause: The original smoke test and health check used curl http://staging.68.220.239.81.nip.io/api/health. The Azure Load Balancer IP can change when nginx-ingress is reinstalled (the CI workflow reinstalls it on every deploy). If the new IP differs from the hardcoded nip.io hostname, all external URL checks produce HTTP 000 (connection refused) or time out entirely. Even with a retry loop (12 × 15 s), the checks failed because the root cause was connectivity, not transience.
Retry loop added: 12 attempts × 15 s = 3 minutes. Still failed — external IP mismatch is not a transient error.
Fix: Replaced all external URL checks with in-cluster kubectl exec. The pod is identified by label selector app.kubernetes.io/name=trophic-mission-control; kubectl wait --for=condition=Ready confirms pod health before the exec; then curl -sf http://localhost:3000/api/health | grep -q '"status":"ok"' runs inside the container.
Result: Smoke test and health check are now completely independent of LoadBalancer IP, ingress, DNS, and external network routing — they test the application layer only.
Decision — Standalone seed script with pre-computed bcrypt hash Design choice

The original seed.ts required bcryptjs and tsx at runtime to hash passwords. The Next.js standalone build only copies @prisma/client, prisma, and .prisma into the runner image — not bcryptjs or tsx. Running the TypeScript seed inside the Kubernetes migration Job would fail with MODULE_NOT_FOUND.

Solution: Created prisma/seed.mjs — a plain ES module using only @prisma/client. The bcrypt hash for demo1234 was pre-computed ($2b$10$XUf8Qv…) and hardcoded as a constant. Users and projects are upserted (idempotent on re-run). Deployments are only seeded when the table is empty. The file ships automatically in the Docker image because the Dockerfile already copies the entire prisma/ directory into the runner stage.
Decision — AUTH_TRUST_HOST and NEXTAUTH_URL hardcoded in CI Design choice

Auth.js v5 rejects requests when the Host header doesn't match the trusted origin. Behind nginx-ingress the pod sees a nip.io Host header, which Auth.js treats as untrusted by default. Additionally, the Key Vault values for NEXTAUTH-URL contained stale trophictech.io hostnames with no update mechanism (no Key Vault write permissions from the pipeline).

Solution: AUTH_TRUST_HOST=true injected into the Kubernetes Secret in both environments. NEXTAUTH_URL hardcoded to the nip.io hostname directly in the workflow rather than reading from Key Vault — eliminating the stale-value problem at the source. Both values are explicit, reviewable, and version-controlled in the workflow file.
Decision — nginx-ingress installed idempotently by CI, not by Terraform Design choice

A terraform destroy removes the AKS cluster, destroying all Helm releases including nginx-ingress. Placing the nginx-ingress install in Terraform would require a separate Helm provider and tightly couples infrastructure and application deployment. The pipeline needs nginx-ingress to exist before every Helm deploy anyway.

Solution: Both the staging and production deploy jobs run helm upgrade --install ingress-nginx ingress-nginx/ingress-nginx --set controller.service.externalTrafficPolicy=Local --wait --timeout 5m as the first step before any application Helm commands. helm upgrade --install is idempotent — it creates the release if absent or upgrades if present. After any infrastructure rebuild, the next CI run fully restores the ingress layer automatically with no manual intervention.
Containerisation

Docker Image Design

The production image is built with a three-stage Dockerfile. Each stage has a single responsibility, keeping the final runner image lean and the attack surface minimal.

Stage 1

deps

Installs all npm dependencies (including devDependencies). This layer is cached by the package-lock hash and rarely rebuilds.

Stage 2

builder

Copies source and runs next build with output: "standalone". Produces the minimal server bundle in .next/standalone.

Stage 3

runner

Non-root user (UID 1001). Copies only: standalone server, static assets, @prisma/client, prisma/ directory, and the migration binary. Healthcheck on /api/health. No devDependencies, no source code.

Why standalone output matters: output: "standalone" traces all server-side imports and bundles only the modules actually used — typically reducing the Node.js module tree by 80–90% compared to shipping the full node_modules. The runner image contains only what the production server needs to start.
Security

Security Posture

Authentication & Secrets

  • Auth.js v5 with Credentials provider and JWT sessions — no OAuth, no external IdP dependency
  • bcrypt password hashing at cost factor 10
  • Role-based access: admin / engineer / viewer enforced in middleware
  • All secrets stored in Azure Key Vault; injected into pods via CSI driver (never stored in container image)
  • GitHub Actions uses OIDC — no long-lived service principal credentials as GitHub secrets
  • ACR admin access disabled; pull access via AcrPull role on kubelet managed identity

Network Security

  • PostgreSQL: private VNet injection only — no public endpoint
  • ACR: private endpoint + private DNS zone
  • Key Vault: private endpoint
  • NSGs on every subnet with explicit allow-lists and DenyAllInBound at priority 65500
  • Azure CNI + Azure Network Policy: pod-to-pod traffic restricted at kernel level
  • TLS 1.2 minimum enforced on PostgreSQL
